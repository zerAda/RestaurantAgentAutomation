Create `db/ci-assertions/17-tenant-resolution.sql` (target: n8n DB; run with
`psql -v ON_ERROR_STOP=1 -d n8n -f ...` AFTER the channel_identities migration + FK-parent seed).
Header comment matching the Phase-16 file style, then three DO-blocks:

(1) KNOWN identity resolves to the correct tenant — mirror the resolver's exact WHERE clause:
    DO $$
    DECLARE v_tenant_id uuid; v_restaurant_id uuid;
    BEGIN
      SELECT tenant_id, restaurant_id INTO v_tenant_id, v_restaurant_id
      FROM channel_identities
      WHERE channel = 'whatsapp' AND identity = 'CI_WA_PHONE_NUMBER_ID' AND is_active = true
      LIMIT 1;
      IF v_tenant_id IS NULL THEN
        RAISE EXCEPTION 'FAIL: known identity CI_WA_PHONE_NUMBER_ID did not resolve';
      END IF;
      IF v_tenant_id <> '00000000-0000-0000-0000-000000000001'::uuid THEN
        RAISE EXCEPTION 'FAIL: resolved to wrong tenant: %', v_tenant_id;
      END IF;
      RAISE NOTICE 'PASS: known WA identity resolves to correct tenant %', v_tenant_id;
    END $$;

(2) A second KNOWN identity on a different channel (instagram / CI_IG_PAGE_ID) resolving to the same
    canonical tenant — same shape, asserts the IG/MSG path is also covered.

(3) UNKNOWN identity returns 0 rows (fail-closed lookup behavior):
    DO $$
    DECLARE v_count integer;
    BEGIN
      SELECT COUNT(*) INTO v_count
      FROM channel_identities
      WHERE channel = 'whatsapp' AND identity = 'UNKNOWN_RANDOM_ID_XYZ' AND is_active = true;
      IF v_count <> 0 THEN
        RAISE EXCEPTION 'FAIL: unknown identity resolved — expected 0 rows, got %', v_count;
      END IF;
      RAISE NOTICE 'PASS: unknown identity returns 0 rows (fail-closed verified)';
    END $$;

Optionally add a 4th DO-block proving an `is_active = false` row does NOT resolve (UPDATE one sentinel
to is_active=false in a sub-transaction, assert 0 rows, ROLLBACK) — only if it stays a single file
runnable with ON_ERROR_STOP. Keep it simple; the three blocks above are the minimum.
  </action>

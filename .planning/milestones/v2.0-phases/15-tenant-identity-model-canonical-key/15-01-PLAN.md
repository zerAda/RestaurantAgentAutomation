    1. Front-matter / header: title "ADR 0001: Canonical Tenant Key — tenants.tenant_id (UUID)",
       Status: Accepted, Date: 2026-06-20, Phase: 15, Requirement: TEN-01.

    2. ## Context — State the keystone problem verbatim: the platform has two structurally disjoint
       tenant_id systems in the same Postgres instance:
         - Data plane (n8n DB): `tenants.tenant_id uuid PRIMARY KEY` with FK-enforced `uuid NOT NULL`
           columns on orders/restaurants/api_clients/conversation_state/outbound_messages.
         - Entitlement plane (strapi DB): `tenant_entitlements.tenant_id` (Strapi-created VARCHAR, no FK)
           and `entitlement_audit_log.tenant_id VARCHAR(255) NOT NULL`, both currently holding the
           literal string 'default'.
       Note the failure mode: comparing 'default' against a uuid column throws
       `invalid input syntax for type uuid: "default"` or silently returns zero rows.

    3. ## Decision — State plainly: `tenants.tenant_id` (UUID) is the single system of record / canonical
       tenant key for the entire platform. The entitlement plane stores the SAME UUID in string form.
       The canonical UUID for the first (and currently only) tenant in CI/dev is
       `00000000-0000-0000-0000-000000000001` (seeded by db/bootstrap.sql:2510-2517), with
       restaurant_id `00000000-0000-0000-0000-000000000000`.

    4. ## Reconciliation: 1:1 mapping — Document Option A (chosen): store the UUID-as-string in the
       existing VARCHAR(255) entitlement column (no ALTER TABLE, no FK required in Phase 15). Record
       Option B (migrate column to `uuid` + FK) as DEFERRED to Phase 16/19 with the reason: it needs the
       live-safe migration apparatus (CREATE INDEX CONCURRENTLY + lock_timeout) and Strapi may regenerate
       the auto-created column on next boot. Include the canonical mapping table:
       `tenant_entitlements.tenant_id 'default'  ->  '00000000-0000-0000-0000-000000000001'` (1:1).

    5. ## entitlement_audit_log.tenant_id Type Decision — Record EXPLICITLY: KEEP `VARCHAR(255)` through
       Phase 15. Rationale: the table is created by the unapplied SaaS migration
       (db/migrations/2026-04-06_saas_modules_entitlements.sql:45-54) and has NO writers yet; changing
       the type now would require the Phase 16 live-safe migration apparatus and the table does not need
       a FK until Phase 19 wires writers that validate the value before insert. Decision: migrate to
       `uuid` with a nullable FK to tenants(tenant_id) in Phase 19, mirroring the
       `admin_audit_log.tenant_id uuid NULL REFERENCES tenants(tenant_id)` precedent (db/bootstrap.sql:987-988).

    6. ## Schema confirmation — Record that `tenant-entitlement` schema.json DEFINES `tenant_id` as
       `{"type":"string","required":true}` (Open Question 2 from research is RESOLVED): the seeder's
       `where: { tenant_id: ... }` maps to a real DB column; Strapi is creating the column. Cite
       inventory-cms/src/api/tenant-entitlement/content-types/tenant-entitlement/schema.json:13-17.

    7. ## VPS backfill caveat (🔴 DEFERRED) — Record the one decision the research demanded the planner
       surface: the production/VPS backfill MUST discover the live tenant UUID at runtime via
       `SELECT tenant_id FROM tenants LIMIT 1` against the n8n DB and use THAT value. It MUST NOT hardcode
       `00000000-0000-0000-0000-000000000001` — that UUID is a CI/dev seed value only. Mark VPS execution
       as deferred to a prod-connected session.

    8. ## Consequences — List: (a) the guard/workflows can compare apples-to-apples once Phase 17 resolves
       real UUIDs from channel_identities; (b) Phase 15 also fixes the seeder (Plan 15-03) and backfills
       CI rows (Plan 15-02); (c) Phase 19 owns the audit-log type migration and the audit writers.

    Do NOT run any SQL, do NOT edit the seeder, do NOT edit any migration — this plan is the ADR only.

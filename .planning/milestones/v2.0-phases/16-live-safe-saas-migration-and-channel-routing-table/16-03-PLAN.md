<objective>
Wire BOTH Phase 16 migrations into the existing `db-migrate` mechanism and prove the whole thing in CI
across two databases. Three problems to solve (all diagnosed in 16-RESEARCH.md):

1. **Strapi-DB delivery gap.** `db-migrate` defaults to `PGDATABASE=n8n` (`docker-compose.base.yml:160`)
   and applies `db/migrations/*.sql` via pgbouncer. But the live-safe SaaS migration (Plan 16-01)
   targets the **strapi DB** and its `tenant_entitlements`/`product_modules` tables do not exist in the
   n8n DB. **Decision (per phase brief):** add a dedicated `db/migrations-strapi/` directory and a
   SECOND apply pass in the `db-migrate` command with `PGDATABASE=strapi`, reusing the existing
   apply-loop pattern. Do NOT route the strapi migration through the n8n pass.

2. **CONCURRENTLY vs pgBouncer.** `CREATE INDEX CONCURRENTLY` cannot run inside a transaction block,
   and pgBouncer runs `POOL_MODE=transaction` (`docker-compose.base.yml:87`). **The strapi pass must
   run direct to `postgres:5432`** (bypassing pgbouncer) so the CONCURRENTLY index builds in the
   migration succeed.

3. **schema_migrations placement (per phase decision):** create a SEPARATE `schema_migrations` table
   IN the strapi DB (idempotent `CREATE TABLE IF NOT EXISTS`) — do NOT cross-DB track.

Purpose: Make both migrations deliverable through one `docker compose up` and continuously verified by
a two-DB CI gate, completing DB-01 (wiring half) and TEN-02 (CI-gate half).
Output: An edited `db-migrate` service (two passes) + a new `phase-16-assertions.yml` CI workflow.

🔴 VPS-DEFERRED: executing both migrations against production Postgres is deferred to a prod-connected
session. This plan is fully local/CI-verifiable.
</objective>

<!-- The existing db-migrate command (paraphrased from docker-compose.base.yml:132-152). The strapi pass mirrors this loop. -->
EXISTING n8n PASS (keep unchanged in behavior):
  export PGPASSWORD=$(cat /run/secrets/postgres_password)
  wait for: pg_isready -h pgbouncer -U n8n -d n8n
  psql -h pgbouncer ... CREATE TABLE IF NOT EXISTS schema_migrations (...);   # in n8n DB
  for f in /migrations/*.sql (sorted): if not in schema_migrations -> psql -h pgbouncer < f ; INSERT filename

NEW strapi PASS (append after the n8n pass; run DIRECT to postgres):
  # schema_migrations lives in the strapi DB now (separate table, per decision)
  psql -h postgres -p 5432 -d strapi ... CREATE TABLE IF NOT EXISTS schema_migrations (...);
  for f in /migrations-strapi/*.sql (sorted): if not already applied ->
     psql -h postgres -p 5432 -U n8n -d strapi -v ON_ERROR_STOP=1 < f   # direct => CONCURRENTLY works
     INSERT filename into strapi schema_migrations (ON CONFLICT DO NOTHING)
  Volume: ./db/migrations-strapi:/migrations-strapi:ro

CONCURRENTLY routing rationale: the strapi migration file contains bare top-level
  `CREATE UNIQUE INDEX CONCURRENTLY IF NOT EXISTS ...` statements. Under `psql -f` each statement
  auto-commits (psql does NOT wrap -f in one txn unless BEGIN is present), so CONCURRENTLY works
  PROVIDED the connection is not pgbouncer transaction-pooled. Hence the strapi pass uses `-h postgres`
  (direct), never `-h pgbouncer`.
</interfaces>

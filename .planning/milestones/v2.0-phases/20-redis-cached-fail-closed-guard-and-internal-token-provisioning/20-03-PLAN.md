<objective>
Make a `GUARD_ERROR_FAILCLOSED` condition (cannot-determine: token missing / Strapi down) distinguishable
from a legitimate `NO_ENTITLEMENT` denial in alerting (GRD-01 criterion 4) — so a missing/expired token
PAGES on-call rather than masquerading as a routine business denial and silently becoming a total outage.
The classification is a PURE, downstream `scripts/guard/classify-deny.mjs` seam keyed off the guard's
already-stable reason prefixes; this plan does NOT touch `W0_MODULE_GUARD.json` (O-3 — disjoint from 20-01).

Purpose: GRD-01 criterion 4. The guard already emits distinct reason prefixes (`GUARD_ERROR_FAILCLOSED:`
vs `NO_ENTITLEMENT:`/`MODULE_NOT_FOUND:`/`EXPIRED:`), but every denial is currently logged identically —
a missing-token total outage looks exactly like a tenant simply lacking a module. A tiny pure classifier
maps each prefix to a severity + pageable flag (with an unknown reason defaulting to pageable HIGH so a
new failure mode is never swallowed), documented to wire into the existing `security_events` severity +
`W8_OPS` `ALERT_WEBHOOK_URL` alert plane — no new alert system, no guard-topology edit.

Output: `scripts/guard/classify-deny.mjs` (pure seam), `scripts/guard/__tests__/classify-deny.test.mjs`
(`node --test`), `docs/guard-alert-split.md` (the severity contract + the downstream wiring), and an
appended classifier job in `phase-20-assertions.yml`. These files are DISJOINT from 20-01 (the guard JSON
+ decision seam) and 20-02 (compose/env/preflight). This plan makes NO workflow edits (O-3).

🔴 VPS DEFERRED (do NOT attempt): activating the alert wiring on the live n8n (the actual
`security_events` severity write + the `ALERT_WEBHOOK_URL` fan-out from the classifier) happens when the
updated workflows are imported on prod — documented here, executed in a prod-connected session.
</objective>

scripts/guard/classify-deny.mjs exports (pure ESM, ZERO n8n/Strapi imports):
  classify(reason: string) -> { class: string, severity: 'LOW'|'MEDIUM'|'HIGH', pageable: boolean, alertKey: string|null }

  Mapping (match by stable PREFIX; case-sensitive on the documented prefixes):
    reason.startsWith('GUARD_ERROR_FAILCLOSED')              -> { class:'cannot-determine', severity:'HIGH',   pageable:true,  alertKey:'GUARD_FAILCLOSED' }
    reason.startsWith('NO_ENTITLEMENT')                      -> { class:'denial',           severity:'LOW',    pageable:false, alertKey:null }
    reason.startsWith('MODULE_NOT_FOUND')                    -> { class:'denial',           severity:'LOW',    pageable:false, alertKey:null }
    reason.startsWith('EXPIRED')                             -> { class:'denial',           severity:'LOW',    pageable:false, alertKey:null }
    reason.startsWith('GUARD_ERROR:')  (input/caller error)  -> { class:'caller-bug',       severity:'MEDIUM', pageable:false, alertKey:null }
    // also tolerate the cache-hit suffix variants ENTITLED_CACHED/GLOBAL_ENABLED_CACHED as ALLOW (not a deny) → {class:'allow', severity:'LOW', pageable:false}
    anything else / '' / null                                -> { class:'unknown',          severity:'HIGH',   pageable:true,  alertKey:'GUARD_UNKNOWN' }
      // SAFE DEFAULT: an unrecognized reason pages (a new failure mode must NOT be silently swallowed).

Canonical reason examples (from the guard / 20-01 seam — the classifier must classify these correctly):
  'GUARD_ERROR_FAILCLOSED: ECONNREFUSED'        -> pageable HIGH GUARD_FAILCLOSED
  'NO_ENTITLEMENT: tenant=… module=channel_whatsapp' -> LOW, not paged
  'MODULE_NOT_FOUND: channel_whatsapp'          -> LOW, not paged
  'EXPIRED: tenant=… module=… expired=…'        -> LOW, not paged
  'GUARD_ERROR: tenant_id not provided (UNKNOWN_CHANNEL_IDENTITY)' -> MEDIUM, not paged
